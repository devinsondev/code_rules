# Gradle and Windows build rules

## 1. Always prefer the project wrapper

On Windows, if `gradlew.bat` exists in the project root, use it.

Preferred commands:

```powershell
.\gradlew.bat --version
.\gradlew.bat :app:assembleDebug
```

For a different module, use that module's task, for example:

```powershell
.\gradlew.bat :composeApp:assembleDebug
```

Do not require or install a global Gradle when the project wrapper exists.

For this workstation's fixed local paths and helper BAT convention, also read `LOCAL_WINDOWS.md`.

## 2. Wrapper belongs to the project

A complete Gradle Wrapper normally includes:

```text
gradlew
gradlew.bat
gradle/
  wrapper/
    gradle-wrapper.jar
    gradle-wrapper.properties
```

Commit these files to the application's repository.

`gradlew.bat` alone is not a complete reusable wrapper.

The wrapper version is project-specific and should be defined by that project's `gradle-wrapper.properties`.

## 3. Do not copy a random wrapper between projects blindly

Reusing wrapper files is technically possible, but only when the target Gradle version is compatible with that project's Android Gradle Plugin / Kotlin setup.

Prefer generating or updating the wrapper for the actual project, then committing it there.

The reusable repository `code_rules` should contain rules and helper-script templates, not a frozen wrapper binary tied to one Gradle version.

## 4. Java and Android SDK on Windows

Before diagnosing Gradle as broken, check:

```powershell
java -version
javac -version
$env:JAVA_HOME
$env:ANDROID_HOME
```

General rule: portable repositories should not hardcode machine-specific JDK paths.

**Single-workstation exception for these projects:** repositories intended only for the configured workstation may use the fixed paths from `LOCAL_WINDOWS.md` inside helper BAT files.

Do not hardcode full repository paths; scripts should use their own directory via `%~dp0`.

## 5. First wrapper run

The first invocation may download the exact Gradle distribution declared by `gradle-wrapper.properties`.

This is expected wrapper behavior.

Prefer the standard Gradle distribution URL generated by Gradle, typically under:

```text
https://services.gradle.org/distributions/
```

Do not replace it with an arbitrary mirror without an explicit reason.

## 6. Missing wrapper

If an Android/Gradle project has no wrapper:

1. determine the Gradle version compatible with the project's Android Gradle Plugin;
2. generate a wrapper using an available compatible Gradle installation/bootstrap;
3. add the complete wrapper files to the project;
4. commit them;
5. from then on, use `.\gradlew.bat` on Windows.

Do not make every developer repeat bootstrap work after cloning.

## 7. Build result

A successful `gradlew.bat --version` only proves the wrapper launches.

It does **not** mean the APK was built.

For a standard Android app, actually build with:

```powershell
.\gradlew.bat :app:assembleDebug
```

Only treat the APK as built after the assemble task succeeds.

Typical debug APK location:

```text
app\build\outputs\apk\debug\app-debug.apk
```

The exact path may differ by module/build configuration.

## 8. Source-control rule

For Android/Gradle applications, the wrapper should normally be version-controlled.

After generating it, include:

```powershell
git add gradlew gradlew.bat gradle
```

Project helper scripts such as `build-debug.bat` and `install-debug.bat` should also be committed.

Do not add Gradle caches, APK outputs or generated build directories.
